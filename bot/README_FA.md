# مرکز کنترل VPN

ربات مستقل تلگرام برای فروش و مدیریت اشتراک VPN که از هر دو ارائه‌دهندهٔ `vpn-ui` و `VPN Panel` پشتیبانی می‌کند. نسخهٔ 1.2.0 ربات مستقل را جایگزین کنترلر تلگرامی قدیمی پنل می‌کند و قابلیت‌های فروش، کیف پول، سفارش، تمدید، مدیریت مشتریان و مدیران را حفظ می‌کند.

> **وضعیت: نسخهٔ توسعه‌ای؛ برای فروش زنده آماده/تأییدشده نیست.** تست‌های محلی و API mock جای تست با Telegram و پنل واقعی، بررسی امنیت عملیاتی، تست بازیابی و پرداخت واقعی را نمی‌گیرند. درگاه آنلاین پیاده‌سازی نشده است.

## امکانات فعلی

- ثبت چند ارائه‌دهنده: `vpn-ui` و `VPN Panel`؛ پنل‌های قبلی به‌صورت خودکار `vpn-ui` باقی می‌مانند.
- `vpn-ui`: credential رمزنگاری‌شده، Base Path، تست اتصال، تشخیص 2FA با TOTP و Sync inboundها.
- `VPN Panel`: اتصال HTTPS با JWT، الزام نقش `superadmin` و لایسنس داخلی معتبر؛ شناسایی ۸ سرویس L2TP، PPTP، OpenVPN، SSTP، IKEv2، OpenConnect، VMess و VLESS از `protocol-overview`.
- مدیریت کاربران VPN Panel از API واقعی `/api/users`؛ ایجاد، ویرایش، حذف امن پروتکل، محدودیت حجم/دستگاه/انقضا، ریست مصرف و تحویل با `sub_link` معتبر. API مصرف را به‌صورت total می‌دهد و تفکیک ساختگی Upload/Download نمایش داده نمی‌شود.
- مشاهده و مدیریت inboundهای شناسایی‌شده: ساخت پایه، تغییر نام/پورت/وضعیت و حذف با تأیید.
- مشاهده و Sync کلاینت‌های inbound؛ فعال/غیرفعال‌سازی، حذف و تغییر محدودیت حجم/زمان/دستگاه برای identityهای قابل‌شناسایی.
- تحویل فایل کانفیگ اختصاصی از endpointهای مستند پنل برای OpenVPN، WireGuard-C، AmneziaWG، GRE و SSH؛ در صورت شکست دریافت، وضعیت به‌صورت صریح به مشتری اعلام می‌شود.
- Core status/install و مدیریت Xray VPN Outbound از endpointهای پنل؛ تنظیمات outbound فعلاً JSON دستی است.
- Core، Xray Outbound و ساخت/تغییر Inbound فقط برای vpn-ui نمایش داده می‌شوند؛ این عملیات برای VPN Panel در دسترس نیستند.
- مشتریان، وضعیت حساب، اشتراک‌ها، موجودی و اصلاح دستی کیف پول با ثبت علت.
- نقش‌های `owner`، `admin`، `finance` و `support`؛ مالک اصلی از `ADMIN_TELEGRAM_IDS` می‌آید و از منوی ربات حذف‌شدنی نیست. Super Admin می‌تواند مجوزهای هر ادمین زیرمجموعه را از داخل ربات به‌صورت جداگانه روشن/خاموش کند.
- پلن‌های فروش، سفارش، دریافت عکس رسید، بررسی مدیر، کیف پول، خرید، تمدید و تلاش مجدد provisioning ناموفق.
- دفترکل کیف پول با کلید idempotency، AuditLog برای عملیات مدیریتی/مالی و ذخیرهٔ رمزنگاری‌شدهٔ payload کلاینت.
- بخش «مشخصات من» با آیدی عددی و دکمهٔ کپی یک‌کلیکی، موجودی کیف پول، تاریخچهٔ کامل و صفحه‌بندی‌شدهٔ سفارش‌ها و فهرست اشتراک‌های فعال؛ هر کاربر فقط تاریخچهٔ حساب خودش را می‌بیند.
- ارتقا/تنزل سوپرادمین دائمی در دیتابیس با تأیید و AuditLog؛ مالک اصلی محیطی قابل حذف نیست. فهرست مدیران صفحه‌بندی شده و تغییر وضعیت مدیر تأیید دومرحله‌ای دارد.
- پاک‌سازی ورودی فرم‌ها و promptهای موقت، همراه با حفظ پیام‌های مهم پرداخت و رسید؛ فایل‌های کانفیگ در گروه‌های مرتب ارسال می‌شوند و در صورت شکست گروهی، ارسال تکی امتحان می‌شود.
- نشانگر انیمیشنی سبک برای مرحلهٔ تحویل فایل با fallback متنی؛ شکست ارسال فایل به‌عنوان تحویل موفق گزارش نمی‌شود.

## نقش‌ها و دسترسی

| نقش | دسترسی |
|---|---|
| `owner` | همهٔ بخش‌ها، از جمله پنل، مشتری، پلن، سفارش، مدیران، تنظیمات و کیف پول |
| `admin` | پنل، مشتری، پلن، سفارش، آمار و کیف پول؛ بدون مدیریت مدیران |
| `finance` | مشتریان، سفارش‌ها/پرداخت‌ها، تنظیمات پرداخت، آمار و کیف پول |
| `support` | مشاهده و جست‌وجوی مشتریان و آمار؛ بدون تغییر مالی یا عملیاتی |

مجوز callback و پیام‌های مراحل مدیریتی مجدداً بررسی می‌شود؛ در صورت لغو دسترسی در میانهٔ فرم مدیریتی، وضعیت FSM و prompt موقت پاک می‌شود. `/cancel` برای خروج از فرم همیشه در دسترس است. ارتقای مدیر عادی به سوپرادمین فقط توسط سوپرادمین معتبر و با تأیید صریح انجام می‌شود و منبع دسترسی در دیتابیس ذخیره می‌شود تا پس از restart باقی بماند.

## راه‌اندازی محلی

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
```

مقادیر لازم محیط تولید:

```dotenv
APP_ENV=production
APP_SECRET_KEY=<random-secret-at-least-32-characters>
DATABASE_URL=sqlite+aiosqlite:///./var/vpn_manager.db
BOT_TOKEN=<telegram-bot-token>
ADMIN_TELEGRAM_IDS=<numeric-telegram-id>
PANEL_CREDENTIAL_ENCRYPTION_KEY=<fernet-key>
LOG_LEVEL=INFO
```

برای توسعه، migration را اجرا و سپس ربات را با `python -m vpn_manager.bot` اجرا کنید. API مبتنی بر FastAPI نیز جداگانه در ماژول `vpn_manager.main` قرار دارد.

## نصب Ubuntu و یکپارچه‌سازی با پنل

در نصب تازهٔ VPN Panel روی Main Server، `install/install.sh` پس از تأیید سلامت پنل، پوشهٔ `bot/` را به‌عنوان منبع محلی به نصب‌کنندهٔ ربات می‌دهد. ربات در `/opt/vpn-control-center`، با کاربر `vpnmanager`، سرویس مستقل `vpn-manager-bot` و virtualenv جداگانه نصب می‌شود. این مسیر به Python نسخهٔ `3.12` تا قبل از `3.15` نیاز دارد؛ virtualenv پنل هرگز استفاده نمی‌شود. نصب اولیه برای دریافت توکن تلگرام و شناسهٔ مدیر به ترمینال تعاملی نیاز دارد. روی Nodeها نصب نمی‌شود.

برای نصب مستقل ربات روی میزبان جداگانه، در ترمینال تعاملی:

```bash
curl -fsSL https://raw.githubusercontent.com/AmiRaiZo/VPN-Control-Center/main/bot/install.sh | sudo bash
```

نصب‌کنندهٔ مستقل آخرین GitHub Release پایدار را با تگ نسخهٔ مشخص دانلود می‌کند و اگر سورس Release در ساختار monorepo باشد، پوشهٔ `bot/` را به‌عنوان ریشهٔ پروژه انتخاب می‌کند. توکن ربات و شناسهٔ عددی مالک مستقیماً از ترمینال دریافت می‌شوند؛ توکن در shell history یا آرگومان پردازش نوشته نمی‌شود، با Telegram `getMe` بررسی می‌شود و فایل `.env` با مجوز `0600` ذخیره می‌شود. سرویس `vpn-manager-bot` فعال و فرمان `sudo vpn-help` نصب می‌شود.

در ارتقای پنل، اگر سرویس ربات از قبل نصب شده باشد، `install/update.sh` به‌روزرسانی محلی و بدون prompt ربات را از `bot/` اجرا می‌کند. فایل `.env`، پوشه‌های `var/` و `backups/`، دیتابیس SQLite و virtualenv ربات در همگام‌سازی کد مستثنا هستند. قبل از ارتقا نسخهٔ پشتیبان داده گرفته می‌شود؛ در شکست آپدیت، کد و فایل systemd قبلی بازگردانده و سرویس دوباره راه‌اندازی می‌شود. نسخهٔ پشتیبان داده برای بازیابی دستی در `backups/` باقی می‌ماند.

اگر Python سازگار یا ترمینال تعاملی موجود نباشد، نصب پنل ادامه پیدا می‌کند و نصب ربات با دستور دستی گزارش می‌شود. نصب واقعی Ubuntu و systemd در این آماده‌سازی اجرا نشده است.

```bash
sudo systemctl status vpn-manager-bot
sudo journalctl -u vpn-manager-bot -f
sudo vpn-help
```

نصب‌کننده در صورت وجود `.env`، کلید Fernet معتبر را حفظ می‌کند. از حذف/تعویض `PANEL_CREDENTIAL_ENCRYPTION_KEY` خودداری کنید؛ تغییر آن بدون rotation داده‌های رمزنگاری‌شدهٔ قبلی را غیرقابل‌بازیابی می‌کند. نصب واقعی Ubuntu در این مرحله تأیید نشده است.

## پیکربندی ربات

1. با `/start` همه منوی فروش را می‌بینند؛ فقط مدیران دکمهٔ «پنل ادمین» را در انتهای منو دارند. `/admin` نیز فقط برای مدیر مجاز است.
2. در «پنل‌ها» آدرس، Base Path، نام کاربری و رمز پنل را وارد و در صورت درخواست پنل، Seed مربوط به TOTP را ثبت کنید.
3. پس از Sync، inboundهای معتبر در فهرست سرویس‌ها ظاهر می‌شوند.
4. در «پلن‌ها» برای یک سرویس فعال، مدت، حجم (GB)، تعداد دستگاه و قیمت (ریال) تعیین کنید.
5. در «تنظیمات فروش»، متن راهنمای پرداخت کارت‌به‌کارت و اطلاعات لازم برای مشتری را ذخیره کنید.
6. مشتری پلن را انتخاب می‌کند، سفارش می‌سازد و عکس رسید را با UUID کامل سفارش در Caption می‌فرستد.
7. مدیر مالی/مدیر مجاز رسید را بررسی و تأیید یا رد می‌کند. فقط پس از تأیید، provisioning اشتراک اجرا می‌شود.

خرید کیف پول، شارژ دستی با رسید و تمدید نیز از منوی فروش در دسترس‌اند. سفارش‌های پرداخت‌شده/درحال‌پردازش اکنون از بخش مدیریت سفارش‌ها قابلیت بازیابی دارند؛ شارژ کیف پول با کلید idempotency قابل بازیابی است. بااین‌حال reconciliation خودکار و scheduler دائمی هنوز پیاده‌سازی نشده‌اند.

### منوی نگهداری سرور (`vpn-help`)

پس از نصب، با `sudo vpn-help` این عملیات در SSH در دسترس است: تغییر Super Admin ID با تأیید دوباره، افزودن مدیر زیرمجموعه با نقش پایه، تغییر توکن پس از اعتبارسنجی Telegram، بررسی آخرین GitHub Release و ارتقای نسخه همراه با پشتیبان‌گیری، و حذف کامل با واردکردن عبارت `REMOVE`. تمام منوها، promptها و پیام‌های SSH به انگلیسی هستند. تغییر شناسهٔ مالک و توکن مستقل از یکدیگر است و هرکدام حتی وقتی مقدار دیگری هنوز تنظیم نشده باشد ذخیره می‌شود. اگر سرویس systemd وجود نداشته باشد، منو صریحاً اعلام می‌کند که تنظیمات ذخیره شده‌اند اما ربات اجرا نیست و نصب باید تکمیل شود؛ پیام موفقیت یا فعال‌بودن سرویس به‌اشتباه نمایش داده نمی‌شود. مجوزهای جزئی هر مدیر از داخل ربات قابل تغییر است. به‌روزرسانی فقط از Release دارای تگ `vX.Y.Z` انجام می‌شود؛ در صورت یکسان بودن تگ نصب‌شده، تغییری نمی‌دهد.

## اتصال به vpn-ui و محدودیت پروتکل‌ها

Adapter از Session Cookie پنل استفاده می‌کند، Base Path را رعایت می‌کند، برای API هدر `X-Requested-With` می‌فرستد و پاسخ `success:false` را خطا می‌داند. در payload کلاینت، `totalGB` طبق قرارداد بررسی‌شده بایت و `expiryTime` زمان Unix بر حسب میلی‌ثانیه است.

وجود یک پروتکل در فهرست شناخته‌شده به معنی تضمین ساخت و تمدید خودکار آن نیست. ساخت client برای همهٔ پروتکل‌ها در پنل زنده آزمایش نشده و پروتکل‌های دارای ساختار اختصاصی مانند `wg-c`، `awg`، `gre`، `mtproto` و `hysteria` ممکن است به تنظیمات تکمیلی نیاز داشته باشند. محدودیت `limitIp` در API تعداد IPهای مبدأ هم‌زمان را کنترل می‌کند، نه هویت قطعی دستگاه؛ در WireGuard/AmneziaWG/GRE تعداد slot و config به `userLimit` سطح inbound وابسته است و از پلن به‌تنهایی قابل تضمین نیست. inbound creation فعلی نیز فرم پایه است و تمام stream/network/TLS/Reality options را پوشش نمی‌دهد.

## عملیات و پشتیبان‌گیری

- فایل DB پیش‌فرض: `var/vpn_manager.db`.
- کلیدهای `.env` را جداگانه و امن backup کنید؛ بدون هر دو کلید برنامه، بازیابی credentialهای رمزنگاری‌شده تضمین‌شده نیست.
- قبل از backup از SQLite، یک snapshot سازگار بگیرید یا سرویس را موقتاً متوقف کنید؛ backup/restore drill خودکار در نسخهٔ فعلی تکمیل نشده است.
- وضعیت migration: `alembic current`؛ اعمال migration: `alembic upgrade head`.
- لاگ سرویس: `journalctl -u vpn-manager-bot`.

## وضعیت اعتبارسنجی و موارد ناتمام

تست‌های خودکار شامل مدل‌ها و migration، دفترکل، TOTP، setup ربات، کنترل API با mock، provisioning mock، پروفایل و جداسازی تاریخچه کاربران، ماندگاری و audit سوپرادمین، صفحه‌بندی/تأیید مدیران، گروه‌بندی و fallback ارسال فایل و انیمیشن هستند. اتصال زنده Telegram و vpn-ui، تمام پروتکل‌ها، پرداخت واقعی، Ubuntu/systemd واقعی، concurrency چند مدیر، lifecycle زمان‌بندی‌شدهٔ انقضا و backup/restore واقعی هنوز تأیید نشده‌اند. سیستم پرداخت فعلی کارت‌به‌کارت و بررسی دستی است، نه درگاه پرداخت آنلاین.

فهرست جزئی‌تر و معیار پذیرش در [`docs/IMPLEMENTATION_STATUS.md`](docs/IMPLEMENTATION_STATUS.md) نگهداری می‌شود.
